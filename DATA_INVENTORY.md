# Data Inventory

Repository snapshot: 2026-09-29. Read-only source review, not a production database inspection. No database queries, backup commands, migrations, account actions or network integrations were executed. No personal record values or credentials are reproduced here.

Read with [LEGAL_COMPLIANCE_SPEC.md](LEGAL_COMPLIANCE_SPEC.md), [INITIAL_COMPLIANCE_AUDIT.md](INITIAL_COMPLIANCE_AUDIT.md) and [LEGAL_REVIEW_REQUIRED.md](LEGAL_REVIEW_REQUIRED.md). This inventory identifies observable data classes and unresolved decisions; it is not an approved retention schedule or privacy notice.

## Evidence and visibility conventions

- **Code + SQL:** application references and checked-in schema identify a data path. Production installation, current rows, grants, storage ACLs and actual deployment remain unverified.
- **Code:** observable readers/writers or files; where schema is missing, that limitation is explicit.
- **Foundation SQL:** platform tables are represented in migration source; that does not prove deployment, use by legacy routes or readiness for arbitrary tenants.
- **Public:** source exposes data without an application login or SQL includes public SELECT policies. **Authenticated**, **own**, **Admin/service** describe inspected controls, not a completed access-control audit. Service-role reads bypass RLS and require endpoint-level review.
- Sensitivity is an engineering triage classification, not a statutory designation. Names, public results and pseudonymous identifiers can still identify people. Handicaps are golf performance records; no medical-data classification is inferred.

For every row with no approved duration in the inspected repository, retention is **TBD — policy decision required**. Technical token expiry, processing-queue removal, date filters, archive status and foreign-key cascades are not retention policies.

## Cross-system deletion and retention decisions still required

1. Identify the accountable data owner, actual deployed tables/policies, hosting/storage regions, subprocessors and lawful/policy purposes for each class. Do not infer live configuration from migration comments.
2. Define a retention trigger, duration, expiry mechanism and permitted exceptions for each row. No retention period is supplied by this inventory.
3. Distinguish account deletion, profile unlink, participant removal, tournament ownership transfer, score correction, media takedown and event deletion. Each has different effects.
4. Map primary data to public API responses, localStorage, static/generated files, Git history, caches/CDNs, R2, email/Auth vendors, derived stats/odds and backup exports. Plan exceptions and restore behavior, not just SQL cascades.
5. Validate participant rights for people entered by organizers without accounts. Identify a request intake/contact process and appropriate verification before export/deletion.
6. Verify operational controls in an authorized environment as a separate task. This review did not read secrets, personal production rows, credentials or backups and did not run database tests.

## Not established by this inventory

No implemented card-payment/billing/subscription provider flow, dedicated analytics store, versioned policy-acceptance ledger, general user export or account-deletion request workflow was identified in the inspected paths. This is a bounded negative finding, not proof that no external/manual process exists. Platform plans/entitlements, operator backups and signup/invite failure cleanup do not establish those workflows.
