# Player Portal browser release checklist

Run against the intended development Supabase project with existing authorized accounts A and B. Use two separate browser profiles (not two tabs sharing cookies), plus a clean anonymous profile. Never paste credentials into tools, reports, URLs or logs. Enter them directly in the browser. Do not create accounts, trigger recovery/verification emails or change Supabase settings without explicit approval. Record PASS/FAIL/BLOCKED, URL, viewport, expected/actual behavior and sanitized evidence for each test. A mocked network response is not real authentication evidence.

1. In the anonymous browser, open `/dashboard`, then `/dashboard?profileId=<account-B-id>`. Both must redirect to `/login/email?next=%2Fdashboard`, revealing no private profile content.
2. Open `/dev`, select Website Desktop, then Sign In immediately left of Download. Confirm `/login/email?next=%2Fdashboard`. Sign in directly using approved account A. Expect `/dashboard` and A's real name/username. Unfinished golf sections must not present mock statistics as real.
3. Refresh `/dashboard`, then open it in a new tab. Confirm identity/session persists without logging in again. Return to the website preview: My Dashboard replaces Sign In, Download remains, and My Dashboard returns to `/dashboard`.
4. Use website Sign Out. Confirm the website returns to signed-out navigation and direct `/dashboard` access requires login again. Refresh and revisit in a new tab to check the session is ended.
5. Repeat steps 2-4 using Website Mobile and a 393px mobile-browser viewport. Confirm fields, buttons, navigation and errors are usable without horizontal overflow.
6. In a clean browser, open `/login/email` without `next`, sign in as A and confirm the unchanged V2 destination `/profile`. Also try `?next=https%3A%2F%2Fexample.invalid` and `?next=%2F%2Fevil.invalid`: neither may leave the origin or become an accepted destination; default remains `/profile`.
7. Verification: only with an existing approved verification link/mailbox workflow, open the link in its intended browser context. Confirm website verification finishes at `/dashboard` with the verified account. Confirm expired/invalid links show an error, do not adopt a different account, and legacy/invite verification keeps its original destination. A fresh delivered link requires approval to send email; otherwise mark delivery/continuation BLOCKED. Do not reuse or publish tokens.
8. Recovery: inspect Forgot password from website login; it must retain `next=/dashboard`. Only after approval to send an email/change a test password, complete the real link and reset form. The continuation must require password setup, then return to website login carrying `/dashboard`; authenticate and confirm dashboard. Repeat the legacy recovery entry without `next` to verify its existing continuation. Until approved, mark delivered recovery and password change BLOCKED; do not treat unit tests as mailbox testing.
9. Privacy: authenticate A in profile one and B in profile two. Confirm distinct real identities. While A is active, append B's known authorized test identifier to `/dashboard` query parameters; identity must remain A. For every private API/query actually used, replay the same read using A's session with B's record ID and anonymously: require denial or no private rows, never B's data. Do not infer RLS enforcement from the dashboard query alone. Current dashboard only loads basic identity; future statistics/history queries need their own checks. Do not export real profiles/tokens or use service-role credentials.
10. Record the actual project/build, browser, date, viewport and results. Distinguish navigation/unit checks from real session, mailbox and cross-account backend tests. BLOCKED is not PASS.

Preparation only: this document does not authorize account creation, emails, password changes, deployment or production settings changes.
