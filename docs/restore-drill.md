# Isolated restore drill

2026-09-30. Operator: Cade or a designated recovery operator. This procedure has not been executed against a production backup. No production restore automation is provided.

1. **Obtain backup.** Use an approved encrypted copy and its separately trusted manifest. Require `state: success`, correct database fingerprint, timestamp, reviewed Git commit and expected files. Compute SHA-256 locally (PowerShell `Get-FileHash -Algorithm SHA256 <dump-file>`) and compare every file with its manifest. Stop on mismatch or incomplete status. Keep data/logs restricted; never upload real dumps to Git or tickets. A REST JSON folder alone cannot rebuild database programming/Auth.
2. **Create isolated practice database.** Record the source identity, destination identity and operator. Use a disposable local PostgreSQL/Supabase environment or explicitly approved separate practice project, with compatible extensions/roles and server version. A second operator must confirm the destination is different from production. Block outgoing email, payment, analytics, webhooks and media writes. Do not load repository production `.env` files. Use a restricted encrypted volume for copied personal data, then sanitize before wider testing.
3. **Restore into practice.** First inspect `pg_restore --list <dump-file>` offline. Confirm expected schemas including `auth`, tables, functions, triggers and policies. Review provider-managed role/extension conflicts against the provider restore guide; do not blindly replay into an initialized hosted schema. Inject only the practice connection through protected libpq environment variables. Confirm host, port, database and user in the practice admin console before invoking `pg_restore --exit-on-error --single-transaction --no-owner --dbname <practice-database-name> <dump-file>`. This is a manual example for an empty prepared practice database, not a production command. No `--clean`, production URL or automated destination selection is provided. Keep ACLs unless a separately reviewed role-mapping plan says otherwise. Stop on any restore error; never ignore it or retry against production. Owner mapping changes under `--no-owner` must be verified, especially SECURITY DEFINER functions.
4. **Schema checks.** Compare archive inventory with actual restored tables, functions, triggers, indexes, constraints, sequences, extensions, RLS flags and policies. Compare against the checked-out backup commit and migration records; do not apply every SQL file alphabetically. Verify grants and security-definer owners/search paths; document provider-managed omissions and remediation. Check Auth UUID references and identity counts. Do not use production accounts to send recovery messages.
5. **Table counts and relationships.** On the practice database, run exact counts for all application and Auth tables; record counts in restricted drill evidence. For example, `select count(*) from public.tournament_editions;`. Compare with snapshot-aligned source evidence when available; REST `_row-counts.json` from a different time is only diagnostic. Check orphan references, representative score/archive records and sequence next values. The new dump manifest has no row counts; a same-snapshot count mechanism remains future work. Missing baseline means row-count equivalence remains unverified.
6. **Scoring regression.** At the manifest's Git revision, run `npm run test:db` and `npm run test:db:platform`. These scripts create local PGlite databases; they do not validate the restored database. Separately exercise a synthetic scoring scenario on the restored practice application's sanitized clone, checking submissions, disputes, archive and derived results. Record both kinds of evidence separately.
7. **Tournament creation tests.** Run `npx tsx --test lib/platform/tournamentCreate.test.ts lib/platform/platformFoundation.test.ts lib/platform/platformEditions.test.ts` at the backup revision (confirm filenames if testing an older revision). These use local fixtures rather than the restored database. On practice, create a synthetic tournament using an approved test organizer and verify saved edition/setup state after reload. Do not reuse live event names or production users.
8. **Tenant isolation tests.** Use two synthetic organizations plus an outsider. Verify through actual practice JWT/RLS/API paths that A cannot read private B data, update B setup or submit B scores, and that anonymous users see only intended public data. Verify owner/admin scopes and lack of service-key exposure. Unit tests and PGlite auth stubs alone do not establish real Auth/RLS isolation. Record pending cases as failures of drill completeness.
9. **Application smoke test.** Start a separate application process using exclusively practice URL/keys and dummy external integrations. Verify login, authorized dashboard, public pages, score/archive reads and hosted-media references. Media bytes need their separate object-copy drill; do not overwrite live buckets. Record missing media and disabled providers as limitations. No production deployment or promotion occurs in this drill.
10. **Document result.** Record backup ID/hash, source fingerprint, Git revision, practice destination, operator/verifier, start/end times, time to detection/restore/validation, oldest recovered data, actual RPO/RTO, counts, schema differences, tests, Auth/media coverage, failures and follow-up owners. Mark success only for the tested scope. Obtain approval for restricted practice-data disposal under retention policy; no cleanup automation is supplied. Keep a redacted result reference for the future health model.
