# Android and iOS beta staging plan

2026-10-21. Planning only. No hosted project, account, deployment or store release created. Android implementation is isolated in `../maroon-a6-poc`; iOS implementation has not begun.

Use a dedicated staging Supabase project, with its own project reference, URL, publishable/anon key, server-only service-role secret, JWT signing configuration, Auth users, PostgreSQL records and Storage buckets. A separate database schema or a second frontend pointing at production does not provide this separation. Apply reviewed schema migrations to an empty staging database and seed synthetic golfers, trips, rounds and scores. Do not copy production Auth users, credentials, database dumps or storage objects. Preserve the existing Supabase identity model and Next.js API contracts; staging identities are deliberately distinct from production identities.

Create a separate staging Next.js service with staging-only secrets and HTTPS origin, after deployment authorization. Both Android and eventual iOS beta use this same staging backend and identity authority. Server-side keys never enter either binary. Use separate mail credentials and test recipient restrictions, storage credentials/buckets, Maps keys, push credentials/topics, scheduled jobs and any R2 namespace. Disable outgoing production email, SMS, webhooks, billing and analytics integrations. Keep production credentials unavailable to the staging build/runtime identity.

Build configuration must explicitly select local or staging, refuse missing/unknown configuration and have no production fallback. Pin exact allowed backend/Auth/Storage hosts, verify the actual project identity before seeding or migration, and scan the final packaged assets/native configuration for unexpected hosts or secrets. Test redirects and attachment/image URLs as well as API calls. A runtime staging-identity endpoint should identify the environment before login/sync; fail closed on mismatch. These are beta acceptance requirements, not controls already implemented by this document.

| Environment | Application identity | Data and destinations | Distribution |
| --- | --- | --- | --- |
| Current Android local prototype | `site.themaroon.app.poc` | Emulator `10.0.2.2` to local test servers; Supabase `maroon-auth-test`, port 55321 | Debug APK via adb; tied to developer machine |
| Proposed Android beta | Dedicated `.beta` application ID, approved before registration | Dedicated HTTPS staging backend and Supabase; separate accounts, scores, trips, storage | Google Play Internal Testing after approval |
| Proposed iOS beta | Dedicated `.beta` bundle ID, approved before registration | Same isolated staging services, separate device secure storage | TestFlight after a separately authorized iOS phase |
| Production | Existing production identity/configuration | Existing production services, untouched | Outside this task |

Keep environment selection out of ordinary user navigation. Beta accounts cannot authenticate to production and production tokens must fail staging authorization. Verify this with synthetic projects/tokens without signing into or modifying production accounts. Restrict staging access to invited testers, redact tokens/personal data from logs, define retention and deletion owners/dates, and test full test-account deletion including objects, caches, queued scores and backups. Capture build hash, app version, backend revision, schema revision and project identity in every test report. Stop test distribution and revoke staging credentials if isolation fails.

Before first remote beta: provision the approved staging resources; validate RLS and bucket policies; test signup/login/refresh/revocation/recovery, trip membership denial, account switching, persistent offline scoring across process death, reconnect idempotency/conflicts, deletion and permission denial on real devices. The local stack currently omits Realtime: hosted Realtime, suspend/resume, reboot, upgrade and physical-device GPS need their own evidence. A phone cannot use the emulator-only `10.0.2.2` address.

For Google Play Internal Testing, establish the developer account and final beta application ID, configure Play App Signing and protect the upload key outside source control. Produce a non-debuggable signed release Android App Bundle with a new version code, staging-only HTTPS configuration, reviewed permissions and no debug/test hooks or local HTTP exception. Complete the applicable Play Console setup, privacy/deletion destinations and declarations accurately. After explicit upload/distribution authorization, select **Test and release > Testing > Internal testing**, upload the AAB, create an invited tester email list or Google Group (up to 100 testers), add release notes, publish only to that track and share its opt-in link with authorized testers. A debug APK is suitable for local installation, not the Play handoff. Internal Testing is distinct from Internal App Sharing and from public release. Current requirements should be rechecked at upload time: [Google's test-track guide](https://support.google.com/googleplay/android-developer/answer/9845334).

For eventual iOS: obtain a Mac with compatible Xcode, Apple Developer membership, beta bundle ID/provisioning and App Store Connect access. Build the same packaged interfaces against staging; verify Keychain, WKWebView storage, location permissions, background/resume and queued synchronization on iPhone. Only then archive/sign and upload after separate approval. TestFlight supports internal App Store Connect testers; external testing has its own beta review process. No iOS project, certificate or upload is created here. See [Apple's TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/).

Supabase's [environment guide](https://supabase.com/docs/guides/deployment/managing-environments) supports separate staging and production projects. This plan deliberately does not enable automatic production deployment or branch promotion. Unresolved compliance actions remain `review_required`: [feature review](android-a6-phase2-review.md).
